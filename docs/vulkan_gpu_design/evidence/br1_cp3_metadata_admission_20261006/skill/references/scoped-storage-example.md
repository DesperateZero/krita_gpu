# 工作示例：引用归还次数与真实时间收益

这是2026-10-06 Krita BR1的一次冻结优化实例，用于解释方法，不能当作所有项目的架构要求或当前性能数据。原产品`6ffe097909e23adf3afd229a2a14e93986fae00b`，结果`57e59e6b0e53c625b0e4853985a242b5433ca618`。

## 从热点到可实现模型

同一public N1024/K16/B4/h1/H0后次写入只改一行4KiB，却需要16页COW、256KiB物理复制。父子版本都做这些工作，不能把64倍放大全部算成本次管理优化收益。

每次6157次allocator引用归还中，working2640、projection1296、publication633合计4569，占74.21%。实际对象释放很少，并有跨操作/worker/epoch尾。正确问题是相同寿命内部为什么反复保活，不能把74.21%理解成可节省74.21%运行时间，也不能把所有对象放进commit即释放的arena。

原作用域或Data保留一次owner，内部容器显式借用，每次真实allocation继续保留原物理费用与引用；逃逸的目录由arena根接续，map由原budgetAuthority覆盖。预测：32局部根+1发布准备根+20实际free+必要交接E，即53+E；工程目标≤约100次。这是可构造模型，不是数学全局下界。

## 完整consumer与真实回归

矩阵覆盖allocator/rebind、全部嵌套working值、四个局部操作、Data准备/取消/分批清理、目录swap、shard maps和派生allocator。

初版给基类增加rebind，派生MutationAllocator继承后却丢失其MutationLifetime。原终点测试暴露512B残留；LLDB与事件追踪定位4个64B控制块加64B登记。修复是显式rebind回派生本族、保留原Store寿命并添加类型断言；没有放宽归零断言。这个反例说明只审“热点容器”的局部diff不够，但并不要求所有后续任务都使用LLDB或增加新所有权层。

## 预测、结果与剩余

| 观察 | 结果 | 可以说明 |
|---|---|---|
| 目标链 | 4569→54，两块一致，E=1 | 本候选机制接近模型，减少98.82% |
| 全操作 | 6157→1642/1645 | 约73.3%引用减少；3次差来自真实cleanup时刻，不能抹去 |
| 必要预算工作 | 524请求、446 controller成功、988完整fits不变 | 没有靠跳过预算取得收益 |
| ARM K16增量 | 吞吐+5.04%，双侧95%区间[2.78%,7.44%]；CPU节省15.06μs [7.53,19.35] | 固定40对、20顺序平衡块上的局部正收益 |
| CPU诊断 | 目标链deref约6.03–6.38μs→0–0.12μs采样估计 | 原约6μs直接成本消失；额外ref/构造等收益未精确拆分 |
| 正式门 | Fresh K16下界仍不足；native K16 handoff约14.3%/14.9%，未达30% | 不能宣称完整M6完成 |

重插桩数量批次和未插桩时间批次分开。首次分析器错误要求所有块的free时刻一致，修正后分析同一数据并保留旧分析器；没有重跑择样。Rosetta线程CPU时钟只报约wall的2%，未经校准不作物理CPU时间解释，wall吞吐仍可比较。

剩余最大单leaf是988次完整fits，约28.6–30.7μs；预算+owner互斥成本约57–58μs。它是下一候选预算，不是可全部删除的收益。下一步应证明哪些全域检查可在保留超限、动态配置、总额和并发合同下减少，再决定实现。
