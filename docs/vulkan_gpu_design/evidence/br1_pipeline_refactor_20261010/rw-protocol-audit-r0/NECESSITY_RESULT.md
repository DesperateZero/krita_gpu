# 53.451M／3.374ms：必要事实、昂贵表达与可避免工作

产品仍为 **bb62f28b7a9806043ae92a91f58b8856b59bca5a**。本轮新增136个稀疏定价过程、2个只计数过程，原13格共1794次语义/身份/退出检查通过；产品和测试源码改动均为0。完整设计仍归[原蓝图§19.22–19.23](../../br1_pagestore_equivalent_pipeline_20261010/PIPELINE_PLAN.md#rw-necessity-audit)，不新增实施状态矩阵。

**结论：已有明确的算法冗余；最需要重写的是“付费物理对象—私有结果—发布能力”的交接表达，而不是把安全检查逐个去掉。** 单次物理排他、completion查询或domain探查均不足以解释大差额。逐页准备/重建账务、结果快照往返、重复归属查询共同放大了必要责任。但尚不能把全部差额精确三分，更没有证据把未解释部分记成正常管理费。

## 1. 分母与三类金额的边界

继续使用上一生产确认批的同义端点，不用本轮插桩值替换普通库账：

| 互斥端点 | bb62当前 | upstream | 额外成本 |
|---|---:|---:|---:|
| write 指令M / 线程CPU ms | 56.256215 / 3.332914 | 6.038628 / 0.379925 | **50.217588 / 2.952988** |
| read 指令M / 线程CPU ms | 9.223888 / 0.818383 | 5.990227 / 0.397736 | **3.233661 / 0.420647** |
| 读写合计 | 65.480103 / 4.151296 | 12.028854 / 0.777661 | **53.451249 / 3.373635** |

write占额外指令93.95%、额外CPU87.53%。upstream的12.029M/0.778ms已经包含一套可运行的读写/历史实现；它既不是纯memcpy价格，也不是算法下界，不能把它再作为53.451M中的“必要部分”。额外账不含其他前台和process减前台的约2.322ms，后续替代净价仍须包括那些端点。

三类采用**事实与动作**分类，而不是把一个函数整体贴标签：

| 分类 | 已证明什么 | 尚不能填写的金额 |
|---|---|---|
| A 必要 | 旧值/新值与可见性、真实保护、失败原子性、预算等事实必须成立 | **不可约的额外指令/CPU下界仍未知**；未知不等于0 |
| B 必要但实现昂贵 | 同一必要责任当前经过过多表示、对象、查找、锁域与准入事务；已有子责任报价 | 合法替代保留必要部分之后的净差仍未知 |
| C 算法可避免 | 稳定事实被重复证明、未变化账务新建事务、无消费者的中间投影等；已定位数量与成立前提 | 每项实际净省多少仍需完整替代；不把C次数占比乘整桶时间 |

因此不是已经得到“A占x%、B占y%、C占z%”的饼图。机器账将三类精确金额保留为null，同时保存非零的当前责任报价和实际事件量；这避免用看似闭合的百分比掩盖尚未证明的必要成本。

## 2. 哪些工作确实必要

主格为4个寿命×16操作×16页；64次写后各有立即读，write/read端点各16MiB逻辑字节。初始化、undo/redo读在各自端点，不混入这32MiB。

| 必要事实 | 当前仍须保留的工作 | 不能误当必要下界的实现量 |
|---|---|---|
| 输入必须成为Store拥有、可读取的结果 | 消费实际变化的输入，64个外部可见cut，保持显式presence/default语义 | 每页一套operation/token发行、临时descriptor容器并非外部合同 |
| history和旧exact reader不能读到被改写内容 | 保留真实before；对将被复用的allocation做最终reader/owner/ABA排他 | 896次spare retag、192次全生命周期出生/退出是当前实现量，不是全局最小量；不能由此授权未通过M7的原地覆写 |
| 多页准备拒绝不能暴露半结果；接受后不能重放输入 | 私有结果、所需安装存储、动态事实复验、一次联合接受与唯一取消责任 | 先把结果投影成VersionInfo，再重新查回同一个native entry不属于必要事实 |
| 预算、物理占用和拒绝后的债务必须真实有界 | 新payload/实际class变化/确需补充的债务额度须在使用前准入；保留父预算和动态限额合同 | 原已付费对象每次改generation都新建一个零delta reservation并非预算语义要求 |
| read必须在同一个cut取得exact结果并保活到最后访问 | root/overlay选择、逻辑保留、binding寿命、物理pin不能混为一个布尔 | 当前范围数组按shard排序后，每页再二分查位置不是读语义要求 |

物理排他本身有当前报价：896次`tryClaim`约 **0.241M / 0.038ms**。这不是严格下界；但它说明不能仅因为整条physical plan约0.75ms，就说0.75ms都是不可省的排他成本。预检与最终claim之间会解锁，reader可能到达；最终claim不能凭较早的预检删除。

## 3. 新细分价格：昂贵的是哪层表达

[事前定价协议](NECESSITY_PROTOCOL.md)固定17条件×4块×镜像，136过程；1/8调用随机采样、每case实测256空窗口。下表是**当前函数inclusive暴露**，单位M/ms；不是差额分摊，不是净可回收预算。父子不可相加，跨批不拼精确余项。

| 当前责任 | write调用数 | 指令M | 线程CPU ms [探索95%] | 分类与价格限制 |
|---|---:|---:|---:|---|
| 完整physical plan | 1024 | **12.707** | **0.752 [0.702,0.802]** | B的完整候选边界；包括拒绝、ledger、descriptor、native准入等 |
| ledger handoff准备 | 896 | 3.765 | 0.224 [0.204,0.238] | B；含domain/budget，不可与二者重复加 |
| ledger handoff提交 | 896 | 2.285 | 0.177 [0.158,0.197] | B；rekey、账务提交、claim归还，真实身份变更保留 |
| native写准入 | 1024 | 3.035 | 0.202 [0.186,0.222] | A+B+C混合：合法代次/排他必要，重复查询/扫描可改；部分调用位于plan内 |
| descriptor准备 | 1024 | 0.503 | 0.077 [0.075,0.080] | B；layout必要，不必每页重建单项准备表达 |
| descriptor安装 | 1024 | 0.356 | 0.067 [0.056,0.082] | B；进入原entry的绑定可直接贯通，不能删除layout事实 |
| provider/binding物理预检 | 896 | 0.802 | 0.074 [0.070,0.079] | 合法拒绝与真实绑定；不是大头 |
| 最终物理claim | 896 | 0.241 | 0.038 [0.032,0.048] | A责任当前价，不是不可约下界 |
| proof归属查询 | 3968 | **2.832** | **0.287 [0.275,0.298]** | B+C；prepare/accept重复查新/旧能力 |
| 所有completion验证 | 1152 | 0.143 | **0.035 [0.029,0.040]** | 1024固定CPU票据＋128实际provider；不能全删 |
| domain同步 | 1024 | 0.270 | **0.045 [0.026,0.063]** | 本格无dirty provider；消除重复探查空间有限 |
| budget reserve核心 | 1024 | 1.502 | **0.091 [0.082,0.102]** | 新/零费用混合；不是整个账务准备价 |
| publication候选清理 | 64 | 0.639 | 0.076 [0.065,0.087] | 必要释放＋候选表示退出；不是全部seal退出价 |

handoff准备与提交互不嵌套，同批点报价合计 **6.050M/0.401ms**，是整条physical plan中最大的已定价子责任；这不是同义替代收益，也未证明覆盖主格全部异常。单独completion验证只有约0.035ms，不能再当成毫秒级核心方案。逐页预算检查约0.091ms也不等于“逐页账务事务”全部价格；后者还包括prepared-change存储、重复backing/physical查询、claim和rekey。

`physical_commit`报价0.175M/0.051ms，但CPU点扰动10.69%，**CPU价格否决**。read的`range_resolve`为0.322M/0.139ms，指令/CPU扰动12.68%/26.25%，**两项价格均否决**；不据此把read差额强行分摊。所有原值仍保留。

桥接seal本批23.695M/1.392ms [1.157,1.628]，前批19.463M/1.145ms。本批8个过程共抽中79个seal，按1/8概率预期64个；原固定概率扩展估计存在明显抽样数量变异。保留事前估计器，不事后改为归一化值来制造一致。物理计划两批12.909M/0.778ms与12.707M/0.752ms量级一致。以上只有4个独立块；区间不包含系统性观察偏差，不能解释成95%概率“分类正确”或“可回收这么多”。

## 4. 哪些算法工作可以避免，以及不能删到哪里

[独立计数协议](NECESSITY_CENSUS_PROTOCOL.md)使用2个正/反顺序过程，不采用其时间。以下主格计数两次完全一致。

| 事实/当前路径 | 已确认数量 | 可达到的表达与删除目标 | 必须保留/未证明项 |
|---|---:|---|---|
| 已付费spare仍准备新的费用事务 | 896次交接全部为ActivePending；**768次zero delta且已有债务headroom，128次nonzero且需新headroom** | 费用不变的原physical对象携带已有收费/债务责任；原operation成组取得所需动态许可，页内仅消费身份交接 | 768不等于可无条件跳过准入；动态限额/公平性/父预算仍须符合原合同。128次真实补额度不能计为零工作；其当前次数也未证明是最低次数 |
| 每页扫描所有注册provider确认domain变化 | **1024次provider探查，dirty=0、change=0** | 有效期内复用受保护domain cut，变化journal驱动实际变化集合；不按页重建全局探查 | 新provider注册、迁移、异步domain change与预算同时变化时必须失效；单次实测无dirty不是永久稳定证明 |
| native写准入为统计Retiring而遍历版本链 | **1984个版本访问，Retiring=0** | 由原shard在publication状态变化时维护准确的retiring数量，准入读取必要聚合；或证明特定无上限情形无需扫描 | 新增聚合更新/存储成本要扣除，不能只凭H1两点宣称高history渐近净收益；这一扫描仅是3.035M准入桶的一部分 |
| 同一新/旧proof在prepare与accept都做归属查询 | **2×(1024+960)=3968次；CPU路径每次至少1 ledger锁＋1 shard锁，即7936次锁获取** | 原issuer能力/原result直接传递，准备时固定不可变事实；接受只复验解锁后可能变化的head、reader与slot | 锁数由源码路径×实测调用数推导，不是争用时间测量。3968不能全当可删：稳定有效期/取消竞争仍需证明；7936也不代表可直接删7936个锁 |
| 固定readyHostCompletion被每页再次验证 | 1024次，另128次真实provider验证 | 在原operation受保护有效期内验证一次，目标1024→最多64 | 同步CPU票据不能替代generic完成；实际provider128保留。即使删除全部固定查询，暴露量也只占全部0.035ms的一部分 |
| 原native结果→通用VersionInfo→再次查native封印 | 主格1024次CPU封印走此路径，随后发布再次查询 | 原entry的exact结果在一个接受边界形成能力；去掉只服务接口适配的投影往返 | provider incarnation、target/layout、完成与一次消费事实保留；不能推广到未完成mutable/异步producer |
| noop先发行两类页ID，再确认无需写 | 控制case68各1024次，主格是真实changed写 | 同一已准入base完成比较后，为真实变化创建身份；全noop无写结果封印 | **主格收益不能领取noop删量**，隐式default/presence与已有history pending保留 |
| range按shard排序后逐页二分找回ordinal | 主格64次范围capture、1024次页resolve | ordinal直达，临时shard分组只用于锁批次；一个cut与原释放责任 | 真实overlay例外仍需保护。零D改成root保留主要修复控制，本主格每读均有16页overlay，不能把它当主格全额回收 |

更深的区别是：**必要的是“对象已付费、能力确实属于此结果、读者不能与写者冲突”；不必要的是每跨一层都重新构造可以再次证明这些事实的通用事务。** 原账务框架的general case需要准备/取消与动态重验，CPU私有结果却仍承受其多次分解与重组。这是B与C共同的重构对象，不是另造一个绕检查的快速入口。

128次补headroom还暴露了两种费用寿命：`registerBacking`把Fresh reservation消费到实际payload后，debt fallback仍留在调用方的短寿命`KisPageBackingPreparation`，成功准备结束后释放；`commitBackingHandoff`则将首次retag的debt reservation移入原backing记录，供以后复用。由源码可推导，主格每个寿命的两组16页工作buffer首次retag需要补headroom，4×2×16=128，与计数一致；这是一条与聚合计数一致的源码因果解释，未另测逐buffer时间线。可以比较从Fresh到spare延续同一付费责任，但提前保留headroom会改变额度保留时长/压力，不能只省掉128次reserve却忽略这个代价。因而“128次本轮确实付费”不等于“算法必须重新付128次”。

## 5. 当前不应作出的结论与下一设计约束

1. **不能用大量平摊费用为全部53.451M开脱。** 已发现具体冗余和表示放大，当前证据反对“全部已是最小必要管理协议”；也不足以断言全部3.374ms都能收回。
2. **不能把锁争用当作已归因。** 本轮只测函数线程CPU和调用数；未测这些锁的等待因果与hold P99。7936次锁说明组织成本，不能推导7936次竞争或相同等待损失。
3. **不能把简单零delta判断作为完整方案。** 768次零费用支持延续原付费对象、合批计划；完整替代必须覆盖128次补额度、Fresh、late reader、取消、动态domain/预算与最终释放，否则只是又增加一代路径。
4. **不能把read余额宣布解决。** 新微观读观察器失真；原capture约0.22ms仍只作方向性责任价。3.234M/0.421ms的精确机制与必要性金额仍开放。
5. **优先级保持整条“物理目标→结果能力→D接受”**，包含原entry/ledger/metadata/publication的表示统一。域扫描、completion等是随整包删除的冗余，不再单独充当主方案。数量约束先进入原§13的T03–T05/T06–T07；净毫秒预报必须由合法完整替代来定，不能按768/896乘0.401ms。

本轮闭合的是若干竞争解释和实际费用事实，**不是三类金额的最终净账**。A/B/C精确金额、合法替代的净回收、主格之外的CPU控制、安装实际alloc/free、资源峰值/保留时长与真实业务仍开放。M6/M7/M8 0/3、校准2/20、默认关闭不变。

复算：`analyze_necessity.py`、`necessity-analysis.json`、`necessity-classification.json`；原始过程/派生差异/构建命令/库哈希见`necessity-manifest.json`与`necessity-raw-texts.tar.gz`。前192过程归档保持不动。
