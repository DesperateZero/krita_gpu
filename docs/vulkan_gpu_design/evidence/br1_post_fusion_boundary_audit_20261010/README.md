四个current lineage进程独立得到相同数量；所有cold只在成功增加generationsReserved后记身份，关联原Store、surface、页坐标、base/source/target generation、transaction以及包含它的merge：

| 当前投影准备 | 次数 | 已证事实 | 删除判断 |
|---|---:|---|---|
| 第一次触及逻辑页 | 56 | 唯一页集合 | 本候选保留 |

## 3. 来源判别：输入无重叠，剩余任务取包围矩形后产生重算

追加的current/upstream/upstream/current四进程，关联queue add→created walker→collect→实际merge，pointer同时带创建寿命，避免地址复用误配。四次结果完全一致：

| 量 | 输入 | 实际执行 |
|---|---:|---:|
| 同批矩形/任务 | 四批7/4/8/8，共27个互不重叠输入矩形 | 19 merge |
| 请求像素面积求和 | **164128** | **207840** |
| 执行矩形并集 | 164128 | 164832 |
| 已覆盖区域再次访问 | 0 | **43008** |
| 包围矩形额外填入的空隙 | 0 | **704** |

总放大43712像素，为输入的26.63%、当前访问面积的21.03%。这些是矩形工作量，**不是像素变化数量或时间比例**。

例如第一批顶部已执行`(128,40,128,88)`和`(256,40,128,88)`；剩下的右上块及底部窄条被collect合成`(128,40,344,96)`，又覆盖前两块。该批全部overlay捕获的root/transaction、22个精确版本集合摘要一致；第三批46个版本集合亦一致。第四批一个过程在最后merge前已commit（overlay→current epoch2），另一个仍是相同56项overlay摘要；不把跨commit摘要缺失伪装成精确相等证明。

关键原因在现有`collectJobs/joinRects`：以剩余两个矩形的面积和作为baseWork，允许包围矩形带来空隙；空隙中可能正是之前已派发/完成的任务。函数没有原脏区域拓扑，因而“减少job数”可能同时增加像素、页版本及生命周期工作。它沿用upstream，不是新增代码独有缺陷；相同内部任务数不能说明它适合当前更贵的页协议。

本次排除了“27个原始dirtyRects自己就重叠”的解释。也排除了把24次同页不相交更新全部视为像素重复的解释。**已经找到具体可改的工作生成点，尚未确认其净收益达到值得实施的程度。**

## 4. 理想方案与保留边界

在原addJob内先把同一请求列表的同列相邻矩形精确合并，保持约128像素列粒度；后续collect只能合并并集恰为矩形的区域，不能用包围矩形重新补洞。不跨addJob/源更新延迟，不建立完成区域账本，不修改PageStore版本权限。

对本次固定27输入矩形做几何回放，可构造 **16矩形、78页访问、164128像素**，相对实际19/96/207840少3任务、18页访问、43712像素。78是这个可构造表示的计数，既非全局下界，也非尚未执行的产品实测；真实调度可能改变producer分批及后续collect，须重新记录，不能按匹配19通知剔样。

条件时间模型为`18次页准备及其后续管理 + 减少的operation/读选择/交付 + 43712像素重算 − 本批合并/判定成本 − 调度/其它阶段净增`。目前16次重叠cold自身在重观察中仅约0.074–0.093ms，说明**冷准备计数不能代表整个方案的收益**；不得按18/96领取投影3.089ms，也不得领取完整6.390ms。净时间和wall方向仍未知，下一步只准入有界算法原型，不直接改全局scheduler或升生产。

真实canvas链为image通知→DirectConnection→canvas startUpdateCanvasProjection→updateCache→OpenGL builder→retrieveData→projection readBytes，然后才进入projectionUpdatesCompressor。不能把后置压缩解释为前面无读者。这个候选在原请求被派发前调整矩形集合，仍须验证显示覆盖/顺序、首次可见与pen-up、复杂层依赖及取消；五层最终像素oracle不能替代这些边界。
