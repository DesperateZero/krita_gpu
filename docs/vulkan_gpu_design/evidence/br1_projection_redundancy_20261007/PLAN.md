# Projection 重复准备的有限诊断

起点产品128fb32a71（生产同38834c4e26），文档2a94f65dd；接92 §16.141。本包先核定每次merge的页集合与实际代际，再决定是否有足够证据实施共享作用域。旧包冻结，不扩样。

1. 从当前三个TU派生诊断副本：merger标记原clear/composite区间与目标；backend记录声明页集合；PageStore在实际成功准备新generation处记录source/target和原scope。增加观察，不改变业务分支。原库保持，按同编译/link命令用三个替换object形成独立诊断库；验证实际加载和输入哈希。
2. 固定ARM四过程：原库/诊断库/诊断库/原库，各一笔原普通freehand（8段/4更新/4worker）。复用上轮计数夹具，persistent关闭，像素、undo/redo、更新与owner终点保持。120s上限，kill+5s reap，失败保留并停止，不换样。
3. 按merge及实际store区分clear与composite，计算成功准备页的并集/交集和代际source链，核对总数与既有root计数。声明targets不是成功generation数；完整默认删除另列，不能算复制。合并页集合的差只是条件上限，必须扣除读者冻结、独立失败与并发冲突。
4. 原有阶段诊断recorder只给原生CPU/wall上下文，嵌套项不相加，记录观察扰动。用于数量和成本定位的重插桩时延不作为真实收益。若需要计价或候选性能，先登记独立固定协议和可删预测；没有合法完整方案时交付数量上限与条件预测，不虚构收益。

产品修改前冻结实现清单及预测；共享责任必须保留旧读、部分页、并发范围、预算/失败、dirty cut与最终释放。M6资格不因本诊断改变。

加载修正批：首批只执行原库与诊断库两过程，均像素/退出正常，但诊断过程实际加载原image库、零观测事件，故不合格并停止。原因是@rpath请求libkritaimage.21.dylib，诊断目录仅有21.0.0实体。补同名symlink后另开固定四过程v2（原/诊断/诊断/原）；旧样本与失败不替换、不计入有效机制数量，v2完成即停。

低扰动修正批：v2四过程语义均通过，但直接逐事件qInfo与嵌套recorder将projection实际更新19→17、页准备149→143。它证明观察会改变调度/合并工作量，不能用于原业务收益预测。保留v2，去掉热路径JSON和recorder，改固定预分配POD buffer，原native线程CPU/wall时钟只包每次新代际准备与整个clear/composite操作；在fixture所有业务/清理结束后统一dump。另开固定四过程v3（原/诊断/诊断/原），校验实际更新和工作量是否恢复；仍不把插桩时延当速度收益。v3结束后本诊断停止，不再调参换样。
