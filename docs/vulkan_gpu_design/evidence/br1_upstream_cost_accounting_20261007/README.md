# upstream 差距：CPU成本账与一次因果校准

本包回到原目标：解释并缩小同义普通绘画相对upstream的差距。**已经把“管理采样多”推进到进程CPU差额、任务责任和冷准备的实际时间，并找到一个经未插桩对照确认的贡献项；尚未证明剩余差额的全部可删除量，也未完成M6。**

产品仍为`fb57b8b69be74a38602fb2f0cd1c6e4374b843e3`，与`2f22452e2d`源码树相同；外层父`c00b3ae965`，upstream沿用`9a24ae0d8c070884fb013594191002e1a1b39a19`。所有改动只在本证据目录派生源码与实验库，生产/产品测试改动0。[事前协议及两次有界判别追加](PLAN.md)、[原库CPU/wall及诊断账](summary.json)、[任务差额](cpu-difference-ledger.json)、[填充因果结果](fill-summary.json)分别保留身份，不混成同一批。

## 1. 原库差距首先是额外CPU，不能只归咎等待

ARM native、原同依赖真实fixture、4 workers、8 segments、4 update callbacks。各阶段在原计时器外读取`RUSAGE_SELF`和进程CPU时钟；下面为固定8配对16过程的描述统计，不是正式置信区间。所有过程均19次projection更新，像素、undo/redo和析构检查相同。

| Stroke量 | 当前边际中位 | upstream边际中位 | 配对差中位（当前−upstream） |
|---|---:|---:|---:|
| wall，projection-ready | 7.946ms | 3.848ms | **4.208ms** |
| 全进程CPU | 18.232ms | 8.725ms | **9.233ms** |
| user CPU | 15.074ms | 7.481ms | 7.548ms |
| system CPU | 3.348ms | 1.293ms | 1.902ms |

配对stroke wall差范围3.076～4.472ms、CPU差7.660～10.660ms，8对均为正。wall比与CPU比分别中位2.028/2.028。本批不是旧约2.3倍批次的重算，不跨批相减宣称改善。边际中位之差、配对差中位和各子项中位不可相加。

CPU是所有进程线程的总量，可以大于wall。两侧都实际使用多线程；当前额外user/system CPU已经达到不可忽略的量级。仍有非执行时间，不能据此宣布等待不重要，更不能把进程CPU全部分配给前台关键路径。

## 2. 额外CPU集中在两条业务责任，并非均匀撒在所有地方

相同任务边界仅记录wall/thread CPU，两侧各两个过程。每过程均为**937个stroke job、19个merge job**；不是多派发了几倍任务。以下使用同一jobs-only批次的两过程均值，三个CPU差额互不重叠：

| 责任 | 当前CPU | upstream CPU | 差额 | 该诊断批CPU差额的描述性份额 |
|---|---:|---:|---:|---:|
| stroke jobs（含原调度/收尾） | 11.863ms | 8.007ms | **3.856ms** | 38.9% |
| projection merge jobs | 5.184ms | 0.530ms | **4.654ms** | 46.9% |
| 未被这些job区间覆盖的进程CPU | 1.828ms | 0.416ms | **1.412ms** | 14.2% |
| 合计 | 18.876ms | 8.953ms | 9.923ms | 100% |

份额是**诊断CPU差额**，不是wall差额、统计置信度或可删除比例。未覆盖项包含观测边界、调度和其它线程，不将其全称为本笔后台维护。观察jobs已覆盖约98%～99%的stroke wall时间，但这不构成完整依赖图。

当前job累计wall−CPU为8.238/8.330ms，upstream为0.886/1.402ms：存在新增非执行时间，线程间区间可能重叠，不能将这些差额加到4.208ms wall缺口。原job全局读写gate等待本身很短；短区间CPU甚至大于wall，说明时钟开销已不可忽略，不能把这些小区间解释成精确锁CPU。

## 3. 当前写入生命周期的互斥成本

原嵌套计时不能相加。本包诊断副本用线程内栈记录父/子关系；每条记录均核验`self + direct children = inclusive`，按最内层相减，避免重复计价。完整诊断中当前两个过程的CPU账：

| 责任 | 不重叠CPU范围 | 解释 |
|---|---:|---|
| 208个冷代际准备，含provider与payload | **3.929～4.122ms** | 下方各冷子项已包含在内，不再相加 |
| private seal各阶段 | 0.977～1.069ms | 发布/证明/storage/metadata/安装/清理 |
| canonical commit各阶段 | 0.659～0.774ms | 数量随匿名client合并可变，不当作固定可删工作 |
| operation范围、adapter、交付外框 | 1.108～1.178ms | 包含必要可见性/准入及兼容表示责任 |
| prepareWrites循环剩余 | 0.105～0.124ms | 已扣除冷准备子区间 |
| pixel operation body | 2.347～2.365ms | 混合kernel与暖访问合计，不能全叫管理 |
| 其它job区间剩余 | 8.272～8.550ms | 含必要画笔生成、其它像素工作和未拆开的外层责任 |

前五项合计约**7.02ms诊断CPU**，支持把冷准备—seal—commit—adapter作为完整责任研究；它们包含新合同必要费用和观察开销，绝不是7.02ms全可删。进一步拆当前冷准备的独立v2批次：

| 冷准备子项 | CPU范围 | 保留边界 |
|---|---:|---|
| 登记backing、取得binding/pin、terminal核验、private安装 | **0.998～1.005ms** | 一个合并区间，内部尚未分价，不把全项称为重复检查 |
| prepareWriteBase及其数据准备 | 0.451～0.481ms | 原始事件名`cold_claim_and_base`；起点实际在prepareWriteBase前，先行claimEntry仍在残差 |
| backing预留/原解锁再加锁 | 0.319～0.383ms | 含必要容量和终结准备，不等于纯allocator |
| provider两completion与physical adoption准备 | 0.350～0.354ms | 事实寿命仍不同，不能据价格直接删除ticket |
| descriptor | 0.078～0.088ms | 与原storage/metadata合同关联 |
| storage和write plan | 0.071～0.082ms | 原known拒绝/选择保持 |
| provider默认页初始化的原逐像素循环 | **1.062～1.127ms** | 是实际数据初始化，不能再归为纯维护指令 |

这纠正了“所有差额都只是零碎维护成本”的过强解释：确有多层维护叠加，也有新路径触发了单价很高的数据初始化。

## 4. 工作量差异：116次初值填充与额外92代际

独立v2四过程在相同任务/结果下取得：

| 量 | 当前 | upstream |
|---|---:|---:|
| 首次页相关payload | 116次逐像素默认值fill | 116次真实整页memcpy |
| 其中stroke / projection | 56 / 60 | 56 / 60 |
| 其它新代际payload copy | **92次（20 / 72）** | 本写锁COW观察域无对应额外复制 |
| upstream预克隆命中 | 不作为相同量比较 | **0**，116次COW均有payload memcpy |
| 写入冷代际 / upstream写锁COW | 208 | 116 |
| 初始化/上述复制字节 | 3,407,872B | 1,900,544B |

upstream从已准备的默认TileData克隆，当前provider在首次物化时通过`createDefaultTileData→fillWithPixel`写入每像素。原ARM库[反汇编](fill-disassembly.txt)显示4096次循环、每次调用外部memcpy；116页即**475,136次小复制调用**。upstream对应116次整页复制CPU仅0.051～0.054ms，当前默认fill约1.1ms。

当前额外92次真实memcpy只有**0.0635～0.0638ms CPU**；先前provider复制完整区间约0.08～0.09ms也包括allocator/登记等。1,507,328B额外数据移动存在，但它本身不足以解释约9ms CPU差额。值得计价的是额外代际连带的整条协议及单价，而非再按复制次数选点。

116不是当前合同的合法代际下界。upstream不承担完全相同的统一CPU/GPU版本、预算、晚读者和释放合同；92代际中哪些可合并，需要逐项证明冻结/读者/失败边界。不能由两侧计数不同直接删除版本。

## 5. 因果校准：同量批量填充确实追回一部分时间

只在独立`fill-variant`实验库替换原fill循环：复制一个原pixel后，以不重叠的倍增块填满4096像素。原字节量相同，每页4096→13次memcpy；[实验库反汇编](fill-variant-disassembly.txt)核定12次调用加最后一次尾调用。116页算法请求475136→1508。未改变准备/版本/预算/交付代码；本批无生产提交。

原库/实验库各能力过程通过后，固定24配对、12平衡块、48过程；无内部阶段观察器，只有原阶段外的进程CPU读数。20,000块bootstrap、seed261021、各端点pointwise双侧95%：

| 端点 | 减少点估计 | 95%区间 | 配对节省中位 |
|---|---:|---:|---:|
| stroke wall | **6.564%** | **3.634%～9.082%** | **0.597ms** |
| stroke进程CPU | **5.237%** | **3.672%～6.644%** | **1.123ms** |
| redo wall | 33.053% | 31.037%～35.138% | 0.412ms |
| redo CPU | 29.886% | 27.759%～32.030% | 0.414ms |
| undo wall | **−6.313%** | **−12.516%～−0.849%** | **−0.043ms** |
| undo CPU | −6.209% | −11.680%～−1.149% | −0.040ms |
| teardown wall / CPU | −0.975% / −1.133% | 均跨零 | −0.002 / −0.005ms |

CPU节省与事前0.9～1.1ms数量级接近；stroke收益不再只来自计数预测。redo原诊断有56次fill，undo与teardown无该fill调用：redo改善与机制相容，undo变慢不能解释为这个函数在undo中变慢。跨阶段状态、代码布局/调度或统计变动尚未区分，**保留该回退，不以主要端点通过掩盖它，不将实验库升为生产**。各端点相关、未经family调整，重叠端点也不相加。

父/实验stroke边际中位8.102→7.493ms、CPU18.583→17.566ms；这些边际差与配对节省、块比率不同。实验库只覆盖当前真实RGBA8用例，没有完整格式/资源/失败/并发资格。也没有新实验库/upstream直接对照，不从旧2.3比值计算新正式资格。

最终冻结检查发现**fill过程38只有18次projection更新，其余47过程为19**；原像素/8输入/4更新callback/undo/退出均通过。主结果保留全部48过程，不能将其称为全部同内部工作量。另做明确的事后敏感性分析：排除包含该过程的整个平衡块9（四过程），其余22配对/11块仍有stroke wall减少**7.061%[3.928%,9.599%]**、CPU减少**5.610%[4.070%,6.937%]**。因此正向结果不依赖该次更新合并；这不是预注册主结果或独立重复，不据其更高点估计宣传。undo wall敏感性区间跨零，主批回退仍保留且原因未定，不选取更有利的版本作验收。原48过程、v0分析/汇总和冻结断言失败均保存，没有换样或重采。

## 6. 对“核心是否找到”的裁决与下一责任

- **定位更明确**：额外CPU主要进入projection与stroke两条责任，任务数量相同；CPU差额已量化，不再仅依赖样本数。projection约4.65ms是最大已定价业务责任。
- **不是全部均摊维护**：默认首次页走逐像素fill，已用有限因果实验确认约1.1ms CPU/0.6ms stroke贡献。它只是差距的一部分，不能据此宣布核心全部解决。
- **共同协议仍是主要结构候选**：冷准备、seal、commit、adapter在当前诊断中约7.0ms CPU，其中约1.1ms是已定位fill，其余包含必要与重复维护。先核定208代际（特别是projection132）的版本原因与合法交付边界，才能预测结构替代净收益。保持原owner，不新增另一份CPU账本。
- **剩余明确开放**：约1.4ms额外进程CPU尚未被jobs账覆盖；callback body内暖访问与纯kernel未拆开；具体锁等待和真实关键路径未证明；额外92代际的可删比例未证明。不得把这些残差填为零。
- **实施顺序**：批量填充已具备可构造算法与增量收益证据，产品化前必须解释undo负控制并完成真实格式/边界/原控制；大差距主责任继续按投影的冷准备—交付整体成本推进，不能以一个6.6%局部收益替换upstream目标。

“量化存在性”“合法可删量”“实际收益”“阶段通过”分别裁决。当前M6/M7/M8仍0/3、正式校准2/20，metadata分母与完整CP0仍欠，persistent默认关闭。

## 7. 扰动、验证与复现

诊断mode0（有副本分支但关闭记录）当前两过程CPU均值17.584ms，jobs-only18.876ms，完整协议19.618ms，v2更细20.743ms。观察有明显额外成本；这些顺序有限样本不是精确开销校准，不机械扣一个固定偏差。短区间CPU>wall已保留。原库基线及fill因果对照不用这些内部观察器；因果校准为fill贡献提供独立支持，其余子项仍是粗价。

观察使用约20MiB固定BSS容量、线程局部嵌套栈，原资源预算/正式峰值不从它授资格。jobs/协议观察登记4线程，v2因覆盖TileData释放等范围而登记当前6/upstream5线程；关闭观察为0。无溢出/栈错误/未结束事件，所有分析阶段无跨边界事件，父子互斥等式逐条通过。两次独立观察器自检覆盖关闭、嵌套、sleep与异常析构，不替代产品安全测试。原private diagnostic timer在实验库中被替换为此观察逻辑，该库只用于本fixture，不供产品运行。

共88个真实fixture过程、264个QTest passed，所有像素/输入回调/undo/redo/析构及实际加载库检查通过。87过程19次projection更新、上述fill过程38为18；内部工作量差异保留。原库16过程、jobs/协议12过程、payload4过程、fill48过程和各能力过程保持独立；不混样、不扩大至通过。生产相关大矩阵、原PaintDevice stress、Rosetta和正式M6均未重跑，不移用上一轮通过数。
